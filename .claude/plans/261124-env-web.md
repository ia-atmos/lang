# env-web: Atmos in the browser

Material for the session `env-web`, in the repository
`ia-atmos/env-web` (created by the author on 2026-11-24, empty but for a
license). Gathered on 2026-11-24 by the session that maintains the
compiler (`atmos-lang`). It has the request (section 1), what exists
(2), and questions (3). Nothing in section 3 is decided.

**atmos-lang** (its `#118`): recommended `env-web`: the name of the
platform (the browser: DOM, canvas, events), as the other environments
are named after what they expose (`env-sdl`, `env-ray`, `env-iup`,
`env-uv`, `env-esp32`); the program becomes WebAssembly through
Emscripten, never JavaScript. And a point that may change the scope:
SDL in the browser may need no new environment, since Emscripten ships
a port of SDL2, so `env-sdl` built with Emscripten could run Rocks in a
page; `env-web` would then hold only what is the browser's own (the
DOM, the events of the page).

## 2. What exists

- **The compiler** (`ia-atmos/lang`): Atmos to one C file plus a
  prebuilt runtime library (`build/libatmos*.a`); `atmos -c f.atm`
  prints the C; `ATMOS_CC`, `ATMOS_CFLAGS`, `ATMOS_LDFLAGS`; an
  environment is an `.atm` file included first (`-e env.atm`), or a
  dedicated compiler (`make env OUT=... ENV=... ENV_CFLAGS=...
  ENV_LDFLAGS=...`). Numeric options `ATMOS_FLOAT`, `ATMOS_INTEGER`,
  `ATMOS_CLOCK`. Manual: "Execution", "Environments".
- **How a board does it** (`ia-atmos/env-esp32`): uses `atmos -c` and
  compiles the C and the runtime sources itself with its own toolchain
  and flags (`-DATM_NO_CLOCK`, `-DA_STK_MAX=...`); the same route fits
  `emcc`.
- **The API of environments** (`atmos-envs`, `261117-envs-atmos.md`):
  the main loop (`step`, `next`), the clock, how events enter; a
  browser has no loop of its own: it calls back (requestAnimationFrame,
  events), as the reference's "no step (`start`, the browser)" row
  says.
- **SDL**: `ia-atmos/env-sdl` (`sdl.atm`, the bindings, `exs/rocks/`
  with images, sounds, a font and a pause test). Emscripten has
  `-sUSE_SDL=2`, `-sUSE_SDL_IMAGE=2`, `-sUSE_SDL_TTF=2`,
  `-sUSE_SDL_MIXER=2`.
- **Rocks**: `env-sdl/exs/rocks/` and `env-pico/exs/rocks/` (over
  `pico-sdl`).
- **The reference**: `lua-atmos/env-js` and `atmos-lang/web` (Atmos in
  Lua, active in Mar/2026): run a program in the browser, with the code
  passed in the URL; `web` is an editor with a "Run" button. Read them
  for the old plans of the DOM.
- **This container** has `node` (`/opt/node22`) and no `emcc`.

## 3. Questions

- **Scope.** SDL in the browser as a build of `env-sdl` (Rocks with no
  change of its code), the DOM as `env-web`, or both in `env-web`.
- **The loop.** The program cannot block the browser: the runtime's
  main loop becomes a callback per frame (`emscripten_set_main_loop`)
  or Asyncify; how the clock and `await 1s` map to it.
- **Building.** `atmos -c` then `emcc` with the runtime sources, as
  `env-esp32`; or a dedicated compiler `atmos-web`; the numeric options
  (WebAssembly has 64-bit integers and doubles: the default fits).
- **Assets.** Images, sounds, the font of Rocks: preloaded into the
  virtual file system (`--preload-file`).
- **The DOM.** What the old plans were (`lua-atmos/env-js`,
  `atmos-lang/web`); events of the page as Atmos events (`:click`,
  `:key`), elements as values, and how a call into JavaScript is written
  (native code calling `EM_JS` / `emscripten_run_script`).
- **Tests.** Headless: `node` runs the WebAssembly with no DOM; a
  browser test needs Chromium (Playwright is installed in the
  containers).
- **An editor.** Whether `atmos-lang/web` (compile in the page) comes
  back: the compiler itself is C and could be built to WebAssembly.
