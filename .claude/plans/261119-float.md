# atmos-float: the numeric types of a build

Material for the session `atmos-float`, where the author discusses the
numeric types of Atmos as options of the build: the reals of 32 bits
that already exist, and whether integers and reals should be
configurable for different systems (ESP32, Arduino and the like).
Gathered on 2026-11-19 by the session that maintains the compiler
(`atmos-lang`). It has the request (section 1), what was done (2), what
was not checked (3), the alternatives (4), and the questions (5).
Nothing in section 4 is decided.

## 1. The request

A past conversation cannot be moved into a session as turns: each turn
is quoted with its speaker, **Autor:** verbatim, the sessions in
summary.

**sdl-tux** (2026-11-16): SuperTux computes its physics with C `float`.
A port in Atmos with `double` drifts from the original after a few

needs: each operation between two reals rounds to `float`; a literal
`0.1` converts as `0.1f`; integers do not change; `math` uses the `f`
functions; `%.9g` prints a float exactly. Its test: `vy = vy +
(10*100)*dt` with `dt = 1.0/(1000.0/15.0)` reads 15.000001, 30.0000019,
45.0000038.

## 2. What was done

On `main`, commit `4565af1` ("rt : ATMOS_REAL=float"). Full suite
passes (lex 32, ast 90, cases 421, golden 443, rt, env), with ASAN.

| What | How |
|---|---|
| The option | `ATMOS_REAL=float atmos prog.atm`. Any other value than `float` or `double` is an error |
| The type | `AReal` in `rt/atmos.h`: `double`, or `float` under `-DATM_REAL_FLOAT`. `AVal.u.n` is an `AReal`; `a_num` takes one; `a_real(v)` reads one; `a_dbl(v)` still gives a `double` (widened) |
| Arithmetic | The fast path computes `a.u.n op b.u.n` in the type; the slow path (integer with real, `//`, `%`) converts to `AReal` first, as C does |
| `math` | `A_RF(fn)` is `fn` or `fn##f`: `sqrtf`, `sinf`, `powf`, ... |
| Parsing | `tonumber` and the reader of `atmos.load` use `strtof`. A literal of the program is emitted as a C `double` literal and converted by the C compiler, which gives `0.1f` for `0.1` |
| Printing | The fewest digits, from 6 to 9, that give the float back: `0.1`, `0.33333334`, `15.000001`, `30.000002`. `string.format("%.9g", x)` gives the nine digits (`30.0000019`) |
| Serialization | `%.9g` instead of `%.17g` |
| Hash of a real key | Widened to `double` first, so the table code does not change |
| Integers | Unchanged: 64 bits |
| The libraries | The runtime is built four times: `libatmos.a`, `-asan`, `-f32`, `-f32-asan`. The compiler picks the pair by `ATMOS_REAL` and passes `-DATM_REAL_FLOAT` to the program |
| Tests | `tst/cases/real-f32-01` runs under the option; a case may now set variables in `NAME.env`. The whole `cases` and `golden` suites were also run once under `ATMOS_REAL=float`: 859 of 863 pass, and the 4 that differ print reals (`2.3333335`, `1e100` as `inf`) |
| Manual | "Execution" (the variable) and "Types & Values" (the paragraph) |

The test of Tux reads 15.000001, 30.0000019, 45.0000038 with
`%.9g`.

## 3. Not checked

- No environment was built under the option. The C of an environment
  (`env-sdl`, `env-pico`, ...) that reads `v.u.n` or calls `a_num` and
  `a_dbl` should compile unchanged, but a C library of an environment
  that is compiled apart must also get `-DATM_REAL_FLOAT`: the layout
  of `AVal` does not change (16 bytes on a 64-bit host), but the
  meaning of its bytes does.
- Bit-exactness against a C program depends on the host: it needs
  `FLT_EVAL_METHOD == 0` (true on x86-64, ARM, Xtensa) and the same
  `libm` for the `f` functions.
- Time. A timer keeps its clock as a C `double` inside the runtime, and
  a clock literal with whole microseconds is an integer, so `await 1h`
  is exact. A time emitted as a real (`emit @:global (16666.6)`) has 24
  bits: above 16.7 s in one event it loses microseconds.
- A literal with more than 17 significant digits that sits on the
  midpoint of two floats may round twice (text to `double` to `float`).
- `sdl-tux` and `env-esp32` were told; neither has run it yet.

## 4. Alternatives

The question of the author: would configurable real and integer types
make sense for different systems?

What a system changes:

| System | Pointer | FPU | What the types of today cost |
|---|---|---|---|
| Desktop, 64 bits | 8 bytes | double | Nothing: `AVal` has 16 bytes either way |
| ESP32 (Xtensa LX6), ESP32-S3, Cortex-M4F boards | 4 bytes | single only | A `double` is computed in software; a 64-bit integer takes two words; `AVal` has 16 bytes where 8 would do |
| ESP32-C3 (RISC-V), RP2040 (Cortex-M0+) | 4 bytes | none | Every real is software |
| Arduino Uno (AVR, 8 bits) | 2 bytes | none | Does not fit at all: 2 KB of RAM and 32 KB of flash, against 153 KB of code measured for the runtime with a program on the ESP32 |

Options, which may combine:

- **`#A` Integers of 32 bits** (`ATMOS_INT=32`). With reals of 32 bits
  and pointers of 32 bits, the union of an `AVal` has 4 bytes and the
  value has 8 instead of 16: half the memory of every local, stack slot
  and table entry on an ESP32. On a 64-bit host it saves nothing (the
  pointer keeps the union at 8). Costs: overflow at 2^31 (a clock in
  microseconds overflows after 35 minutes: clocks would need
  milliseconds or a 64-bit timer apart), hashes and the number formats
  to review, and one more axis in every test.
- **`#B` No reals** (`ATMOS_REAL=none`). A build with integers only,
  as the integer-only builds of Lua for microcontrollers: `/` is an
  error or the integer division, a real literal is a compile error,
  `math` loses the transcendental functions. It removes the software
  floating point from a board with no FPU. It changes the language seen
  by the program, so a library written with reals does not load.
- **`#C` Fixed point as the real**. A real is an integer with a binary
  point (16.16). Fast with no FPU and deterministic everywhere, but with
  a short range and its own rounding: it is another arithmetic, not a
  size.
- **`#D` A profile instead of separate options** (`ATMOS_TARGET=esp32`
  = reals of 32 bits, integers of 32 bits, a small stack). Easier to
  use and to test (a few named combinations instead of a product), less
  flexible.
- **`#E` Build the runtime on demand**. Four libraries are built today
  and each new option doubles them. The compiler could compile the
  sources of the runtime with the flags asked, into a cache per
  configuration, and only the default would be prebuilt.
- **`#F` The explicit type `float32`**, set aside by the author's
  choice of the build option. It would let one program mix both, at the
  cost of a second kind of real in every operation and in the manual.
- **`#G` An 8-byte value on 64-bit hosts** (NaN boxing, as LuaJIT): a
  representation change, independent of the options above, that halves
  the memory of values on the desktop. It conflicts with `float` reals
  only in that it needs the `double`.

Precedent in Lua 5.4: `LUA_32BITS` (integers and floats of 32 bits,
both at once), `LUA_C89_NUMBERS`, and the choice of the float type
(`LUA_FLOAT_TYPE`) apart from the integer type (`LUA_INT_TYPE`).

A first reading, to be discussed: the pair "reals of 32 bits and
integers of 32 bits" (`#A`), as Lua's `LUA_32BITS`, is what pays on the
boards the project targets (the ESP32), because of the 8-byte value;
`#B` and `#C` serve boards that the runtime does not fit today; `#E`
becomes necessary with the second option.
