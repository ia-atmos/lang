# atmos-iter: iterators, loops and functions

Material for the session `atmos-iter`, where the author wants to
organize the part of Atmos that walks over data: the loops, what can be
iterated, and the functions over iterables (such as the `find` and
`filter` that `atmos-pool` wrote). Gathered on 2026-11-20 by the session
that maintains the compiler (`atmos-lang`). It has the request
(section 1), what exists today (2), how the ports use it (3), and
questions (4). Nothing in section 4 is decided.

## 1. The request

`atmos-pool` wrote `find(xs, f)` and `filter(xs, f)` as two global
functions on its branch `pool` (not merged), for "await until a member
of a pool satisfies a condition": `val t = await :tick until find(ts,
f)`. `atmos-lang` explained them to the author (its `#104`).

## 2. What exists today

On `main` at `61979ce`. Manual: "Loop", "Breaks", "Lambda", "Pipes",
"Where", "Basic Functions", "Vector".

### Loops

```
Loop : `loop´ Block                 ;; infinite
     | `loop´ ID Block              ;; numeric infinite
     | `loop´ ID* `in´ Expr Block   ;; data iterator
     | `loop´ ID? `on´ Patt Block   ;; event loop
```

What `loop ... in e` accepts, by the type of `e`:

| `e` | Ranges over |
|---|---|
| a table | the indexes and values of its vector part, then its other keys and values |
| a pool of tasks | index and task, in the order they were spawned; the body may abort tasks (then not visited) and spawn into the pool (visited) |
| a function | calls to it, until it returns `nil` |
| two numbers `(a, b)` | from `a` up to `b`, inclusive |
| a number `n` | `0` to `n-1` |
| `nil` | `0` upwards, with no limit |

A loop is an expression: `nil`, or the values of `break v` / `until c,
v` / `while c, v`. `skip` goes to the next iteration. `loop on P` awaits
a pattern at each iteration (`loop e on :X`, `loop on 1s`, `loop on 35,
:tic`).

### Functions that take or give functions

- `func`, the lambda `\(a,b) { ... }` and `\{ ... }` (implicit `it`),
  closures (a captured variable that is written is boxed).
- Pipes: `x -> f`, `x --> f(y)`, `f <-- x`; `where`.
- A function iterator is written by hand as a closure that returns
  `nil` at the end (the manual's example counts from `s` to `e`).
- A function cannot await: only a task can. So a function given to a
  library runs to completion at once; a body that awaits must be a
  loop.

### Library

| Where | Functions |
|---|---|
| globals | `print`, `type`, `tostring`, `tonumber`, `assert`, `next(t [, k])` |
| `vector` | `insert`, `remove`, `clear`, `sort(t [, f])`, `join` |
| `string` | among others `string.split`, `string.find` |
| `X` | `load`, `loadx`, `dump`, the structural `X.in` |
| branch `pool` (not merged) | globals `find(xs, f)` (the first member and its key, or `nil`) and `filter(xs, f)` (a new vector), over a pool or a table, with `f(v, k)`; `lib/grid.atm`, a spatial grid in Atmos |

There is no `map`, `fold`, `any`, `all`, `count`, `range`, `zip`,
`keys`, `values`, and no notion of "iterable" in the manual beyond the
table above.

### Rules that bear on a library

- **`pin`** (stable since 2026-11-19, `TODO-pin.md`): a function that
  builds a table and gives it away declares it `val`; a result is
  unpinned and its holder decides. A lazy iterator is a closure over
  the collection: a reference into a pinned value that must not outlive
  it.
- **Pools**: a member is a task that may end while a collection of
  results still refers to it (a dead task is safe to hold; its `pub` is
  gone).
- **Order**: a table is walked vector part first; a pool in spawn order.

## 3. How the ports use it

Counted on 2026-11-20 over the `.atm` files of 15 repositories (ports,
environments), comments left out; approximate, by regular expressions.

| What | Count |
|---|---|
| `loop ... in` | about 1490 |
| of which over a number or a range | about 470 |
| `loop ... on` (event loops) | about 830 |
| lambdas | about 460 |
| pipes | about 730 |
| `loop v in f(...)`, a function as the iterator | about 110 (most used: `ini.load`, `rint`, `enemies_in_circle`, `overlap_list`, `io.lines`, `string.split`) |
| a `loop ... in` followed within three lines by `until` or `break` (a search written by hand) | about 60 |
| `vector.insert` 72, `vector.remove` 35, `vector.join` 31, `vector.clear` 11, `vector.sort` 9 | |
| `next(` | 3 |
| a port's own `find` / `contains` / `remove` helper | 4 |

So the ports iterate mostly with `loop ... in`, write searches and
filters by hand, and already return collections from functions used as
iterators (`enemies_in_circle`, `overlap_list`).

## 4. Questions

- **What is an iterable?** Today it is whatever `loop ... in` accepts,
  decided by type in the runtime. Should a library take exactly the
  same things (a table, a pool, a function, a number, a range), so that
  `find(5, f)` and `filter(io.lines(f), g)` work? Should a user value
  be able to say how it is iterated (a field, a tag), or is "a function
  that returns `nil` at the end" the whole protocol?
- **Where the functions live.** Globals (`find`, `filter`, as on the
  branch `pool`), a library (`iter.find`), or the library of the
  collection (`vector.filter`, `tasks.find`). And with pipes:
  `enemies -> iter.filter(\\{ it.hp > 0 }) -> iter.map(...)`: does the
  pipe put the collection in the right argument?
- **Which functions.** A small closed set (`find`, `filter`, `map`,
  `any`, `all`, `count`, `fold`), or more (`zip`, `take`, `range`,
  `keys`, `values`, `sort`ed copies). What the 60 hand-written searches
  and the functions that build lists in the ports would have used.
- **Eager or lazy.** `filter` giving a new vector (as on the branch), or
  an iterator to be walked by `loop` and chained with no intermediate
  table. Laziness meets the rules of `pin` (a closure over a pinned
  collection) and the pools (members that end while it is suspended).
- **Loops against functions.** A function cannot await, so `map` with a
  body that awaits does not exist. Is the line "a library for what runs
  at once, loops for what takes time", or should a loop get forms of
  its own (a filter in the header, a loop that builds a list, a
  comprehension)?
- **The loop forms themselves.** `loop i in 3`, `loop i in (1,3)`,
  `loop i` and `loop in nil` are four spellings of a counter; a range
  could be a value (`range(1,3)`). Whether `until`/`while`/`break`
  with a value stay as they are. Whether iterating a table should have
  explicit forms for "the vector part only" and "the keys only".
- **Changing a collection while it is walked.** Pools have a rule (the
  manual states it). Tables have none written.
- **`find` over a pool as the condition of an await** (`atmos-lang#1`,
  in `atmos-pool`): whatever is decided here must keep `val t = await
  :tick until find(ts, f)` or give it another spelling.
- **The cost.** A call of a closure per element; the ports are games
  that do this every frame. `doom` and `sdl-snxkx` have the benchmarks.
