# The new rules of `pin`

Plan of the compiler session (`ia-atmos/lang`). The rules were written
in the session "Pin rules discussion" and approved by the author there
on 2026-11-15 (decisions 1 to 5, then "Vá em frente"). This file is how
they are implemented, in what order, and what was added or bent.

## The rules, as approved

**Principle.** Every dynamic value (table, function, native, task,
pool) belongs to a block, and may only be stored where its block lasts
at least as long as the place that stores it. No reference outlives its
scope. The same rules for all dynamic values, tasks included.

**Two states.**

- *Pinned*: owned by a block, which finalizes it at its end.
- *Fresh*: not owned yet (the result of a constructor, a call, or a
  block, before it is declared or stored). It carries a *floor*: the
  innermost block of what it holds. It cannot leave the floor, but may
  be pinned at the floor or in any deeper block.

**Rules.**

1. *Birth.* A value is born fresh, with its floor at the innermost
   block of the pinned values it is born with: the fields of a
   constructor (tagged or not), the operands of `++`, the captures of a
   function, the arguments of a task, the dependencies of a native.
   After birth the floor does not rise: a later store into a fresh
   value is checked against its floor. A task has its floor from birth,
   also during the first run of its body.
2. *Pin.* A fresh value becomes pinned when declared with `pin` (the
   current block) or when stored in a pinned value (the block of the
   holder). The pin is deep: every fresh value it holds is pinned with
   it. A parameter may receive a fresh value, and the callee may pin
   it, store it, or return it.
3. *Store.* A place (a field of a table, `pub`, a variable of an outer
   block, a captured variable, a pool) only accepts a value whose block
   is the same as or outer than the block of the place; for a fresh
   place, its floor. `emit` and `throw` follow the same check. A
   captured variable belongs to the block that declares it, and a
   function that captures it is born with its floor in that block.
4. *End.* At the end of a block, its pinned values are finalized in
   reverse order, interleaved with `defer`. A fresh value that is
   dropped is finalized at once: a table is released, a native is
   closed, a task is aborted.
5. *Result.* The only way to undo a pin is to be the result of the
   block (the last expression, `return`, `break`, `escape`): the value
   becomes fresh in the outer block, and takes along what it holds
   from that block. An error if it holds something that cannot leave
   (a task of a pool that stays).

**Also decided.**

- `val` of a fresh dynamic value is an error: the first declaration is
  always `pin`, and `val` only aliases a value that has an owner.
- Natives follow the same rules, with a C function for a binding to
  declare that a native holds another value.
- The error says the type of the value and the line of its `pin`.
- Not now: the scoped assignment `with m.x = v {...}`.

## How it maps to the runtime

The header of an object has `pinned` and `depth`. Today a value that
is confined by what it holds is marked as pinned at the depth of what
it holds. From now on:

| State | `pinned` | `depth` |
|-------|----------|---------|
| Fresh, free | 0 | 0 |
| Fresh with a floor | 0 | the floor |
| Pinned by a declaration | 1 | its block |
| Pinned by a holder (deep) | 2 | the block of the holder |
| Owned by the runtime (builtins, emitted events) | 1 | 0, or its floor |

- The depth of a value, for every check of a store, is `depth`,
  whatever the state: the check of rule 3 is one comparison.
- `lin`: a new field of the header, the line of the `pin` that gives
  the value its depth, for the message of the error.

## Added or bent (to report)

Kept current while implementing.

- **Events.** The rules do not say who owns a fresh value that is
  emitted. Many tasks may receive it, and each keeps it in a `val`
  after the emit returns, so no receiver can pin it and no block can
  finalize it. Chosen: an `emit` pins a fresh event at its floor,
  owned by no block (released by the count of references, as today).
  So `val e = await :X` stays valid, and a receiver cannot pin the
  event.
- **What is not a declaration.** Parameters may hold fresh values (as
  approved). So may loop variables, which are not `val` declarations.
- **A dropped task that is running** (it is below in the C stack)
  cannot be aborted at the drop: it ends with the trail that spawned
  it, as an unpinned task does today.
- **Tasks held by pinned data** are aborted at the end of the block of
  the holder, before the other finalizers of that block, and not in
  the position of a declaration (they have none).
- **What a task holds.** The `pub` of a task and its final value are
  held by the task: a fresh value stored there is pinned with the
  task, and released with it (at the end of its block; for a task of
  a pool, with the pool). So a task may publish itself with no leak.
  The main task is owned by the runtime, outside all blocks.
- **An emit to all tasks of a value pinned in the outermost block of
  the program** is accepted: all tasks live inside that block. It was
  an error, and with floors it would refuse any event that holds a
  top-level value.
- **Prototypes.** `func f () {...}`, `task T () {...}`, their `val`
  forms, and `set f = func () {...}` are declarations of prototypes:
  each pins its prototype, in the block of its variable (the
  outermost block of the program for a top-level name).
- **A task is pinned from birth** when its block owns it (a spawn
  that is a statement, or the value of a `pin`), and not after its
  first run. Otherwise a task could not refer to what it publishes
  (`set pub = [rect=[...]] ; val rect = pub.rect`) in its first run.
- **A task spawned into a field of a pinned table** (`set G.car =
  spawn Car()`, `pin G = [car = spawn Car()]`) is pinned with the
  table from birth, for the same reason. A spawn in any other
  expression (an argument, a nested constructor) is fresh during its
  first run.
- **A native really holds what `a_nat_holds` declares**: it keeps a
  reference, is always finalized before what it holds (the close of a
  parent waits for its children), pins a fresh parent with it, and
  takes the parent along when it leaves a block. Found wrong by
  `env-pico`, where only the floor was set.
- **`where`.** Its declarations have no modifier. Chosen: the clause
  owns a value that is fresh, and refers to one that has an owner.
- **The fresh check comes first**: `set out = [c]` reports `expected
  pinned value`, and not the escape of `c`.
- **`invalid pin : shared value` is gone**: a value that is pinned is
  refused with `invalid assignment : unexpected pinned value`, and a
  fresh one is accepted whatever its count of references.

## Strange cases met here (for the report)

From the migration of the tests and of the example game in this
repository. The ports add theirs.

1. **A task cannot publish a value pinned in its body.**
   `pin rect = [...] ; set pub = [rect=rect]` is an escape: the `pub`
   is visible outside. The task writes `set pub = [rect=[...]]` and
   then `val rect = pub.rect`. Every entity of a game does this.
2. **A variable cannot receive a fresh table**: `var acc = [0,0]` and
   later `set acc = [0,0]`. Changed in place, or kept as a field of a
   pinned table.
3. **A `val` that fails depending on the caller.**
   `func f (t) { val a = t.x }` works for `f(p)` with `p` pinned, and
   fails for `f([x=[1]])`: what a fresh parameter holds is fresh. The
   function must pin the parameter first.
4. **A value that is sometimes fresh and sometimes owned** fits
   neither `val` nor `pin`: `x || []`.
5. **A closure that captures a mutable local** cannot be stored in a
   table outside the block (a list of callbacks built in a loop). It
   leaves as the result of a block.
6. **`func f () {...}` inside a block** is a variable of the program:
   it fails if it captures a local. `val func` is the form.
7. **A parameter that the callee pins** is released when the callee
   returns: the caller, if it still has the value, sees it empty.
8. **The receiver of an event cannot pin it**, and an event with a
   value of an inner block must be built in the emit.
9. **`pin ok, e = catch`**, for a thrown table.
10. **The error says `expected pinned value` before it says the
    escape**: `set out = [c]`.
11. **A task with a self-reference in its `pub` that nobody pinned**
    (a fresh task kept alive only by its own `pub`) is not detected
    as dropped: it ends with the task that spawned it, and the cycle
    is not reclaimed.

12. **A fresh table that is an argument cannot receive a pinned
    value later**, not even one of the outermost block of the
    program (found by Lessmilk, in the retrieve of its quadtree):

        pin G = [list=[[x=1]]]
        func get (out) {
            loop _, o in G.list { set out@+ = o }   ;; invalid escape
            out
        }
        get([])

    It is rule 1 as approved: the floor of `[]` is set at birth and
    does not rise, since the runtime does not know which block the
    caller keeps the table in. Ways out today: `pin l = [] ; get(l)`,
    or the function creates the table, fills it, and returns it.
    A sound refinement, for the author to decide: let the floor of a
    fresh value rise to the outermost block of the program, since
    every fresh value lives inside it. It would accept the case
    above, and nothing deeper.

## Strange case A, solved (2026-11-17)

The author approved a rule for case A (a variable cannot receive a
fresh value), in the session of the rules: a place that owns its
value may be assigned a fresh one (a `pin` variable, a field of a
pinned table, the `pub` of a pinned task); the new value is pinned in
the block of the place, deep; the old one is finalized when its last
reference goes, at once if the place held the only one, and at the
latest at the end of the block, where a cycle is broken.

How: a value that leaves the place that owned it is *retired*
(`pinned` 4, `a_retire`): the runtime keeps one reference to it in a
list. When the count reaches one (only the list), it is released at
once, and the values pinned with it are retired in turn. At the end
of the block (`a_retired_end`), what is still alive (a cycle) is
finalized as a pin of the block. A task or a pool that leaves its
place becomes as a task held by pinned data: aborted when its last
other reference goes, or at the end of the block. A captured `pin`
that is assigned lives in a box, as a `var`.

Tests: `tst/cases/repin-01`, `repin-02` (the cycle of the session,
loops of 10000 assignments under the sanitizer, natives, the `pub`,
`vector.clear`).

## Strange cases B, C, D, F, and case 7, solved (2026-11-17)

The author approved a ceiling, in the session of the rules, which
reverses decision 2 (`val` of a fresh value is an error) and closes a
hole: a name that held a fresh value (a parameter) let a shorter-lived
owner adopt it, and then saw it finalized (strange case 7).

- A fresh value held by a name (`val`, `var`, parameter, loop
  variable, `where`) gets a ceiling: the block of its outermost name.
  It may only be adopted (a `pin`, a store in a pinned value or a
  `pub`, an assignment to a `pin`) at its ceiling or outside;
  otherwise `invalid pin : table named at f:N`.
- How: `ceil` and `clin` in the header of an object; `a_name` at each
  binding (deep: the fresh values held get it too, and a fresh value
  stored later in a named fresh one); `a_unname` at the end of a block
  for its slots and parameters (a value that only they named loses
  that ceiling, so that a value that leaves its block is not refused
  later); the check before every adoption walks the fresh values,
  with marks for cycles.
- Removed: the compile-time error of a constructor declared with
  `val`/`var`, and the run-time `expected pinned value`. `where` is a
  name again (it pinned before).
- Not done, and it does not fit the words "an implicit pin": a cycle
  among fresh values that no block ever adopts is not reclaimed (a
  `val` does not break a cycle; a `pin` does).
- An approximation: the ceiling of a value that a `var` held and then
  replaced stays (a conservative error is possible later); and two
  parallel trails at the same depth may reset each other's ceiling
  (`a_unname` compares depths, not blocks).
- Cost: a loop of 2000000 `pin t = mk(i)` of two small tables takes
  0.95 s against 0.75 s before (the check walks the fresh value before
  `pin_deep`), and the same loop with `val` takes 0.75 s.

Tests: `tst/cases/ceil-01` (B, C, D, F, a task held by a name, a value
that leaves the block of its name, E still an error, a fresh cycle),
`pin-err-01`, `04`, `05`, `06` (the hole, through a pin, a store, an
inner block, and a held value).
