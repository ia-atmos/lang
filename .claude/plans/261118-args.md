# args: arguments with and without parentheses

Material for the session `args`, where the author discusses one rule for
when the arguments of calls and statements may go without parentheses.
Gathered on 2026-11-18 by the session that maintains the compiler
(`ceu-atmos`), at the author's request.

## 1. How it started

Item 31 of the list of the compiler session: `await x`, for a variable
or a field, is a compile error today (`invalid await : unexpected
expression`); only `await(x)` works. The compiler session recommended
accepting it (a name or a field, never a call, since `await T()` spawns
`T` and `await(f())` awaits the value of `f()`). The author's answer, on
2026-11-18, verbatim:

> 31. os parametros que nao precisam de () vem de lua: 'string',
> [table], etc. o await t fugiria disso. mas varios ja fogem, como o
> return. preciso de uma regra um pouco mais simetrica. crie uma sessao
> `args` para discutir isso. sera que funcoes tb poderiam ser chamadas
> assim? f x,y ?

So the question is broader than `await`: one symmetric rule for calls,
statements, and `await`, and whether `f x, y` should be a call.

## 2. The rules today (`doc/manual.md`)

**Calls** ("Calls"): `f(e1, e2)`, or, as in Lua, a single constructor
argument with no parentheses: a string, a tag, a table, a lambda, a
clock, a native literal (`print "hi"`, `print :ok`, `type []`,
`f \{...}`, `f 'a' 'b'` is `f('a')('b')`). The parser's test is
`check_call_arg` in `src/parser.c`: `[`, `\`, a string, a tag, a native,
a clock. The same formats hold for `await`, `do`, and `tasks`.

**Statements** ("Statement Arguments"): `abort`, `break`, `emit`,
`escape`, `return`, `skip`, `throw`, `until`, `while` take a list of
expressions with no parentheses, which extends as far as possible
(`return x + 1, y` gives two values); the list must start in the line of
the statement, else there is none; `return (1, 2)` is `return 1, 2`, and
`return (f())` keeps only the first value. `abort` and `emit` take one;
`skip` none.

**Await** ("Await"): `await Patt`, where a bare pattern is `[:any |
:all] Expr [Pred]`: a tag (`await :X`), a constructor (`await :X [...]`),
a clock (`await 1s`), a call that spawns (`await T()`), a pool (`await
:any ts`); `await(e)` is the value form (a task, a tag, a number); and
`await <...>` takes a full pattern with `||`, `&&`, `!`, `until`.

**Pipes**: `x -> f`, `f <- x`, `-->`, `<--`.

## 3. The ambiguities the manual already lists (section "Ambiguities")

| Case | What it is | Not |
|---|---|---|
| `await 20min + 1s` | `(await 20min) + 1s` | `await(20min + 1s)` |
| `f` ⏎ `(x)` | `f ; (x)` | `f(x)` |
| `f :X []` | `f(:X [])` | `f(:X) []` |
| `return` ⏎ `f()` | `return ; f()` | `return f()` |
| `return (a+1)*2` | `return ((a+1)*2)` | `(return (a+1)) * 2` |
| `[return a, b]` | `[return (a, b)]` | `[(return a), b]` |
| `val x = 1, y` | `val x = (1, y)` | `(val x = 1), y` |
| `task` ⏎ `(x)` | `task ; (x)` | `task(x)` |

## 4. What a rule must answer

Questions the compiler session sees; the session `args` takes them with
the author:

- Is a statement (`return`, `emit`, `await`) a function call with a
  special name, so that whatever rule calls follow, they follow too? Or
  are statements the only juxtaposed lists?
- `f x, y` as a call: where does the list end (`[f x, y]`, `val a, b = f
  x, y`, `g(f x, y)`)? A binary operator after `f`: `f -x` (a call with
  `-x`, or `f - x`?), `f (x)` (today a call), `f [1]` (today a call with
  a table, not an index). A name alone, `f`, stays the function, not a
  call with no arguments.
- `await x` with `x` a name: it fits a rule where any expression that is
  not a call may follow a statement; it breaks the Lua rule of
  constructors only.
- What changes for code that exists (the 11 ports, `exs/`, the tests):
  every new juxtaposition must keep the meaning of programs that compile
  today, or be a deliberate break with a migration.
- The references: Lua (strings and tables only), MoonScript and Ruby
  (calls with no parentheses), the reference Atmos (`atmos-lang/atmos`)
  and Céu.
